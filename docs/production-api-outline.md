# طرح اولیه API نسخه عملیاتی

این سند قرارداد نهایی API نیست؛ فقط طرح مفهومی برای طراحی backend است. تا زمان دریافت مستندات رسمی سداد، هیچ endpoint یا نام فیلد بانکی در این سند فرض نشده است.

## ایجاد درخواست

`POST /api/v1/payment-requests`

نمونه درخواست از سامانه مبدأ به backend مرکزی:

```json
{
  "merchant_order_id": "ORDER-10025",
  "amount": 1500000,
  "currency": "IRR",
  "description": "هزینه ثبت‌نام",
  "callback_url": "https://origin.example/payments/result"
}
```

نمونه پاسخ مفهومی:

```json
{
  "payment_id": "opaque-server-generated-id",
  "status": "pending",
  "payment_url": "https://pay.example/p/opaque-server-generated-id",
  "expires_at": "2026-12-01T12:00:00Z"
}
```

مبلغ باید در سمت سرور کنترل شود. سامانه مبدأ باید با اعتبارنامه مستقل احراز هویت شود و درخواست تکراری با کلید idempotency مدیریت شود.

## دریافت وضعیت

`GET /api/v1/payment-requests/{payment_id}`

فقط سامانه مبدأ مجاز باید بتواند جزئیات درخواست خود را دریافت کند. پاسخ باید وضعیت داخلی ثبت‌شده پس از تأیید سمت سرور را نشان دهد، نه صرفاً نتیجه بازگشت مرورگر.

## اعلان به سامانه مبدأ

پس از تأیید قطعی تراکنش، backend مرکزی می‌تواند webhook ارسال کند. پیام باید شامل شناسه رویداد یکتا، شناسه درخواست، مبلغ، وضعیت نهایی و زمان باشد و با امضای HMAC یا سازوکار امن توافق‌شده محافظت شود. گیرنده باید امضا را بررسی کند و رویداد تکراری را دوباره اعمال نکند. برای webhook ناموفق، retry کنترل‌شده و ثبت لاگ لازم است.

## چرخه وضعیت پیشنهادی

`created → pending → verifying → paid`

و وضعیت‌های پایان دیگر مانند `failed`، `cancelled` و `expired`. وضعیت `paid` فقط پس از تأیید سرور به سرور از سداد ثبت شود.

## الزامات پیش از اتصال سداد

- دریافت مستندات فنی جاری از سداد/مسیر رسمی پذیرندگی
- دریافت شناسه‌ها و کلیدهای پذیرندگی از کانال امن
- پیاده‌سازی درخواست، بازگشت و تأیید دقیقاً مطابق مستندات
- تست در محیط آزمایشی رسمی در صورت ارائه
- بررسی امضای پیام، TLS، timeout، retry و کنترل تراکنش تکراری
- عدم ثبت اطلاعات کارت و اسرار در logها
